## 1. Cryptographic Key Inventory & Requirements

KAAMSETU utilizes symmetric HMAC-SHA256 and asymmetric Ed25519 cryptographic primitives for identity, rate limiting, and verifiable credential minting.

| Secret Name | Primitive | Min Entropy | Purpose | Storage & Scope |
| :--- | :--- | :--- | :--- | :--- |
| `RATE_LIMIT_HMAC_SECRET` | HMAC-SHA256 | 256 bits (32 bytes) | Privacy-preserving rate limit key derivation & session cookie signing | Server-only (`process.env`) |
| `RATE_LIMIT_HMAC_SECRET_PREVIOUS` | HMAC-SHA256 | 256 bits (32 bytes) | Session token fallback verification during zero-downtime key rotation | Server-only (`process.env`) |
| `CREDENTIAL_SIGNING_KEY` | Ed25519 Private Key | 256 bits (32 bytes) | Cryptographic signing of Sovereign Worker Identity credentials | Server-only (`process.env`) |

## 2. Key Quality Enforcement Rules

In `src/lib/crypto/key-validator.ts`, `validateCryptographicKeyMaterial` and `assertCryptographicKeyQuality` enforce rigorous quality standards before any key material is accepted into runtime memory:

1. **Length Requirement:** Must decode to at least 32 raw bytes (256 bits of cryptographic entropy).
2. **Predictable Pattern Blacklist:** Automatically rejects strings containing:
   - `placeholder`, `password`, `secret`, `kaamsetu-dev`, `12345678`, `abcdefgh`, `default-secret`
3. **Repetition Defense:** Rejects strings with fewer than 10 unique characters (e.g. `aaaaaaaa...`).
4. **Information Leakage Prevention:** In error diagnostics and log outputs, secret values are NEVER printed or echoed; only key name and byte length are reported.

### Validation Example:
```bash
# Valid 256-bit Key Generation Commands:
openssl rand -base64 32
# Output example: k7Q9wP+vM9vT8qY... (44 base64 characters = 32 raw bytes)

openssl rand -hex 32
# Output example: 4f9b8c2d1e... (64 hex characters = 32 raw bytes)
```

## 3. Zero-Downtime Key Rotation Architecture

Session cookies generated by `signSessionToken` carry a 14-day validity window. Rotating `RATE_LIMIT_HMAC_SECRET` without a deprecation window would immediately invalidate all active worker sessions.

Phase 39.3 introduced a dual-key verification fallback in `verifySessionToken` (`src/lib/auth/otp-service.ts`):

```typescript
// 1. Verify against active primary HMAC secret
try {
  const secret = getRateLimitHmacSecret();
  const expectedSig = crypto.createHmac("sha256", secret).update(encoded).digest("base64url");
  const expBuf = Buffer.from(expectedSig, "utf8");
  if (sigBuf.length === expBuf.length && crypto.timingSafeEqual(sigBuf, expBuf)) {
    verified = true;
  }
} catch {
  // Primary verification failed or secret unavailable
}

// 2. Fallback to previous secret during zero-downtime key rotation
if (!verified && process.env.RATE_LIMIT_HMAC_SECRET_PREVIOUS) {
  try {
    const prevSecret = process.env.RATE_LIMIT_HMAC_SECRET_PREVIOUS;
    const expectedSig = crypto.createHmac("sha256", prevSecret).update(encoded).digest("base64url");
    const expBuf = Buffer.from(expectedSig, "utf8");
    if (sigBuf.length === expBuf.length && crypto.timingSafeEqual(sigBuf, expBuf)) {
      verified = true;
    }
  } catch {
    // Previous secret verification failed
  }
}
```

## 4. Production Key Rotation Runbook

Follow this step-by-step procedure when rotating secrets in production:

1. **Step 1 — Prepare Staging of Old Secret:**
   Copy the currently active `RATE_LIMIT_HMAC_SECRET` value from the Vercel Dashboard.
2. **Step 2 — Set Previous Secret:**
   In Vercel Project Settings > Environment Variables:
   Add or update `RATE_LIMIT_HMAC_SECRET_PREVIOUS` with the copied active secret.
3. **Step 3 — Generate & Set New Primary Secret:**
   Generate a fresh 256-bit key:
   ```bash
   openssl rand -base64 32
   ```
   Set `RATE_LIMIT_HMAC_SECRET` to the new generated value.
4. **Step 4 — Trigger Production Redeployment:**
   Redeploy the application so all serverless functions load the new environment variables.
   - All newly signed tokens use the new secret.
   - All existing active sessions verify seamlessly via `RATE_LIMIT_HMAC_SECRET_PREVIOUS`.
5. **Step 5 — Decommission Previous Secret (After 14 Days):**
   Once 14 days have elapsed, delete `RATE_LIMIT_HMAC_SECRET_PREVIOUS` from Vercel Environment Variables.
