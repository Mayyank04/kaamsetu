### 1. Financial Compliance & Tax Framework

All commercial SaaS revenues generated by KAAMSETU comply with Indian Goods and Services Tax (GST) regulations. The billing engine separates tax liabilities into appropriate central, state, and integrated tax components in `public.financial_gst_ledger`.

```sql
CREATE TABLE public.financial_gst_ledger (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  invoice_number text NOT NULL UNIQUE,
  contractor_organization_id uuid NOT NULL REFERENCES public.contractor_organizations(id),
  billing_period_start date NOT NULL,
  billing_period_end date NOT NULL,
  base_amount numeric(10,2) NOT NULL,
  tax_rate numeric(4,2) NOT NULL DEFAULT 18.00,
  cgst_amount numeric(10,2) NOT NULL DEFAULT 0.00,
  sgst_amount numeric(10,2) NOT NULL DEFAULT 0.00,
  igst_amount numeric(10,2) NOT NULL DEFAULT 0.00,
  total_amount numeric(10,2) NOT NULL,
  currency text NOT NULL DEFAULT 'INR',
  is_interstate boolean NOT NULL DEFAULT false,
  hsn_sac_code text NOT NULL DEFAULT '998314',
  payment_status text NOT NULL DEFAULT 'paid',
  created_at timestamptz NOT NULL DEFAULT timezone('utc'::text, now())
);
```

### 2. Mathematical SaaS Metric Purity

A common pitfall in startup financial reporting is the artificial inflation of Annual Recurring Revenue (ARR) by including one-time onboarding fees, hardware card sales, or consulting setup charges.

KAAMSETU enforces strict mathematical purity:

$$\text{ARR} \equiv \text{MRR} \times 12$$

```typescript
export function computeFinancialMetrics(subscriptions: Array<{
  monthlyRecurringFee: number;
  oneTimeSetupFee?: number;
  status: string;
}>): {
  activeSubscriptionCount: number;
  mrr: number;
  arr: number;
  totalOneTimeFees: number;
}
```

- **One-time fees are strictly excluded from ARR**:
  $$\text{ARR} \ne (\text{MRR} \times 12) + \text{One-Time Fees}$$
- If an enterprise account pays ₹9,999/month plus a ₹25,000 one-time onboarding fee, the ARR contributed is strictly ₹119,988, not ₹144,988.

Independently asserted and verified in Phase 13 Test 22.

### 4. Constitutional 0% Worker Commission Database Invariant

To ensure that the zero-commission guarantee cannot be altered by future application code or operational staff, the protection is enforced at the PostgreSQL kernel level:

```sql
ALTER TABLE public.payment_records_ledger
  ADD CONSTRAINT payment_records_commission_zero_check
  CHECK (platform_fee_percentage = 0.00 AND commission_amount = 0.00);
```

#### Test Verification:
In Phase 13 Test 19, an automated transaction attempting to extract a 5% commission (₹50 on a ₹1,000 wage payout) was submitted directly to the database:
- PostgreSQL immediately rejected the row with error code `23514` (`check_violation`).
- Non-zero commissions cannot be persisted under any circumstance.
